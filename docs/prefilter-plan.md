# 前置过滤方案（准入端）：策略与复现范围

> 状态：**策略待确认，尚未改动 `index.mjs`**
> 前置文档：`docs/context-optimization-plan.md`（草案：从「事后清除」转向「准入端选择」）
> 本文把该草案推进到「可实施」：明确复现历史 overclock 的哪一部分、把机制改到产出端的哪里、每步怎么验证。

---

## 0. 一句话

把 0.7.0 之前的 **overclock（每步归档 + 滞后一步清除）** 拆开：**保留并强化它的细粒度归档与单条取回，丢弃它的事后清除与核心补丁**；把「决定工具结果以什么形态进入上下文」这件事从 `step/end` 之后**前移到工具产出时刻**（`tools/post-execute`），并按论文结论用「收据 + 路径」取代「全文 + 事后占位符」。

---

## 1. 先纠正上一轮取证的两处错误

**错误一：幸存者偏差。** 检测脚本用 `os.path.isdir(tool-result-logs)` 当筛选条件，只统计「归档还活着」的会话 —— 出问题的会话归档已删，被静默剔除。

**错误二：方法与现象不匹配。** 我用 80 字符逐字 shingle 去测「模型是否把工具结果写进助手消息」，测出 0.89% 并据此说「现象很弱」。但真实现象是**转述（paraphrase）**，不是逐字复制 —— 逐字匹配在原理上测不到它。

**这个现象本项目早就测过，数据在 CHANGELOG 里**（`CHANGELOG.md` 0.7.0 → Why）：

> 每步清除解决不了「模型把自己的输出当缓存」：实测 ≤49000 字节的已清除结果里，事后复用只有 **5.5%** 走取回、**52.6%** 靠记忆代偿（**41.2% 抄进推理、11.3% 抄进可见正文**），而适配器会把历史推理以 `reasoning_content` 回灌上下文。

更早的观测在已删除的 `usage.mjs`（0.7.0 移除）文件头注释里：

> 实测（本机 5 个会话、173 条被清除结果、5191 个可辨识记号）发现模型几乎不调用 `read_tool_result_log`：它要么把"具体事实"（哈希/路径/数字/报错串）转述进自己的推理，要么直接重跑同一条命令把内容重新打印一遍。于是"取回"这条设计路径的实际命中率接近 0。

**测量方法（必须复用）**：稀有记号判定 —— 从工具结果抽「含数字 / 含 `/` `.`、≥6 字符」的 token，若后续在助手正文、推理或工具入参里重现，且该 token 在已登记结果中出现率 ≤30%，记为一次复用。渠道分五类：`read` / `rerun` / `carryText` / `carryReasoning` / `reuseArgs`。

⇒ 这份文档后续所有「效果」判断都用这套指标，不用逐字匹配。

## 2. overclock 考古：复现对象与丢弃对象

### 2.1 它当时做了什么（源自 `ed8aab1^:index.mjs`，共 1460 行）

| 部件 | 位置 | 行为 |
|---|---|---|
| 逐步归档 | `archiveStep()`（`old:797`）、`stepFileName()`（`old:896`） | 每个 `step/end` 写 `round-NNNN-step-MMM.json`，并在 `index.json` 维护 `steps[]` 清单 |
| 滞后一步清除 | `onStepEnd()`（`old:363`）→ `clearStepToolResults(turn, step-1)`（`old:510`） | 第 N 步结果只对第 N+1 步可见；第 N+1 步 `step/end` 时把第 N 步替换为占位符 |
| 单条取回 | `readByStep()`（`old:1030`） | 优先读 step 文件；老数据回退到整轮文件按 `stepOfEntry` 过滤 |
| 整轮合并 | `collectTurnData()`（`old:1085`） | `round-NNNN.json` + 同轮全部 `-step-` 文件按 `seq` 去重合并，附 `steps` 汇总 |
| 可见性规则占位符 | `clearedText(..., extended, ...)`（`old:708`） | 每轮仅第一条清除附「某一步结果仅对下一步可见」的规则说明 |
| 核心补丁 | `patches/patch-core.mjs` | `dsh-session` 加 `seriesGeneration`（仅非清除型 replace 递增）、`dsh-agent-loop` 改读它 —— 否则每步 replace 都被判成新系列，Chat 每步重渲一次系统提示词 |

### 2.2 为什么被删（0.7.0 给出的三条理由）

1. **方向错**：事后清除治不了「模型把自己的输出当缓存」——52.6% 的结果被转述进推理，而推理会以 `reasoning_content` 回灌上下文（`project_history.md` 已记录：DSH 永远带 `tools`，`reasoning_content` 必须回传）。清掉了 `tool/result`，内容却换了条路留在上下文里。
2. **代价高**：每步清除都要 replace 已发送的前缀 ⇒ 每步一次前缀重建 + 需要改 DSH 核心的补丁。
3. **收益不抵**：每步清除换来的上下文收益，抵不上一个要改核心的补丁（`CHANGELOG.md` 原文）。

### 2.3 复现范围（结论）

| 部件 | 复现 | 理由 |
|---|---|---|
| `archiveStep` + `stepFileName` + `index.steps` | ✅ **完整复现** | 细粒度预留。0.7.0 退化为每轮一文件后，实测模型抱怨取回粒度太粗（a293efee reasoning："The offsets are line offsets into the archive text, not into the individual result. Ugh"） |
| `readByStep` / `collectStepData` / 整轮合并 | ✅ **完整复现** | 单条定位能力，0.7.0 的 `readByStep` 分支当时直接返回「已不再保留逐步归档」 |
| `usage.mjs` 稀有记号归因 | ✅ **复现为观测层** | 唯一能测「记忆代偿/重跑/取回」五渠道比率的工具，前置过滤的效果判断全靠它 |
| `onStepEnd` 滞后一步清除 | ❌ 丢弃 | 这是「事后删除」本身，正是要替换的对象 |
| `clearStepToolResults` / `clearToolResultsWhere` | ❌ 丢弃（保留函数以备回退开关） | 同上 |
| 核心补丁 `seriesGeneration` | ❌ 丢弃 | **前置过滤在 append 端，不改写已发送事件 ⇒ 不需要任何核心补丁**。这是本方案相对 overclock 最大的减法 |
| 可见性规则占位符 | ❌ 丢弃 | 语义随新机制重写 |

> 复现的代码不直接照抄：`readByStep` 依赖的 `index.steps` 保留；`archiveStep` 的入参从 `(session, turn, step)` 改为「产出时刻的单条结果」，见 §3.4。
>
> **【落地差异 · 2026-09-28】** 上表的「✅ 完整复现」是按**能力**说的，形态与实现不同：`index.steps` / `stepFileName` / `archiveStep` **未落地**，改为 `index.json` 的 `results[]` + `results/t<TTTT>-s<SSSS>-<NN>-<tool>-<callId>.txt`；单条 / 逐步定位由 `readByTurn(turn, step)` + `collectTurnData` 提供，**没有** `readByStep` / `collectStepData` 同名函数；`usage.mjs` 观测层**未落地**；「保留函数以备回退开关」也**未保留**（代码里没有 `clearToolResultsWhere` / `clearStepToolResults`）。

## 3. 前置过滤：策略设计

### 3.1 落点：`tools/post-execute`（已查证的一等扩展点）

```
'tools/post-execute'(
  this: Scoped<ToolRuntime>,
  exec: ToolExecution,
  result: Readonly<ToolExecutionResult>,
  next: () => Promise<PostToolDecision>,
): Promise<PostToolDecision>
```
返回 `{ kind: 'accept', content: [...] }` 可替换**模型可见内容**（不可同时替换 `value`；失败结果不可替换 `value`）。调用点 `dsh-tools/lib/index.js:3378`，签名 `lib/types/index.d.ts:61`。

**与现有插件（`session/event` 监听）的本质差别**：

| | 现有插件 / overclock | 前置过滤 |
|---|---|---|
| 时机 | 结果已进入 surface 之后（`turn/end` / `step/end`） | 结果 materialize **之前** |
| 操作 | replace 已发送的前缀（retroactive） | append 端决定形态 |
| 缓存代价 | 每次替换 = 一次前缀重建（a293efee 实测 8 个轮边界共 78,646 miss token） | **0**（从不改写已发送内容） |
| 需要核心补丁 | overclock 需要 | **不需要** |
| 与 CliffCompaction 一致 | ✗（改写了已发送内容） | ✓（只截断/丢弃，从不改写历史） |

### 3.2 分级规则（草案，参数待定）

> **【已被实现取代 · 2026-09-28】** 本表是早期草案，与 0.8.0 实现不符：实现里**没有** `meta.shape` / `caps` 信号（只用「工具名 + 是否纯文本 + 字节数」）；`edit` / `write` **不是**豁免规则（只是返回体通常 ≤1024 才自然通过）；`grep` / `glob` **没有**「命中计数」、`web_fetch` **没有**「正文提取」，一律是通用头部预览；阈值是 **1024 字节**（非 8192 / 20000）。实现的实际形态见 `index.mjs` 的 `onPostExecute` 与 `README.md §准入规则`。

准入判定用三个信号：**工具名 × 结果形状（`meta.shape`/`caps`）× 字节数**。

| 工具 | 准入形态 | 依据 |
|---|---|---|
| `read` | **原样放行**（保留 DSH 的 `offset/limit` 分页与 51200 字节上限） | 内容就是下一步的必需输入；spill-policy 也显式跳过 `read` |
| `edit` / `write` | 原样放行 | 返回体是确认信息，本来就小 |
| `bash` | 超阈值 → **保尾 + 收据**（尾部是最终状态/错误；落盘取全文） | `dsh-bash-local` 已是「每流 64000 字节 + 保留尾部」，方向一致，只是阈值更高 |
| `grep` / `glob` | 超阈值 → **前 N 条命中 + 命中计数 + 收据** | DSH 已做条数截断（250 / 100）并落盘，本方案只把阈值按「准入」重设 |
| `web_fetch` | 超阈值 → **正文提取 + 收据** | 一次性数据（抓完即用），复用概率最低 |
| `read_tool_result_log`（若保留） | 原样，但受 `RENDER_BUDGET_BYTES` 约束 | 见 §3.5 的取舍 |
| 其他 / 未知 | 超阈值 → 通用收据化 | 兜底 |

**草案参数（待用户定）**：阈值取 `8192` 码点（对齐 DSH 内置 pruner 的 `thresholdChars`）还是 `20000` 字节？分段取 head/tail 多少行？

### 3.3 收据的四要素

1. **是什么** —— 工具名 + 关键参数摘要（复用现有 `hintOfArgs`）
2. **多大** —— 字节 + 行数（按字节，不按字符，避免中文低估）
3. **在哪** —— **文件路径**（绝对路径，可直接喂给 `read`/`grep`）
4. **怎么取** —— 一行可复制的取回命令提示（`read <path> offset/limit` 或 `grep <pattern> <path>`）

收据里**不加**「已清除/已删除」这类词 —— 实测模型把「已清除归档」读成「没了」，于是转述或重跑（`project_history.md` 记录的 a293efee turn8 reasoning 原文）。

### 3.4 落盘结构：复用 overclock 的文件布局

> **【已被实现取代 · 2026-09-28】** 实现**不用** `round-NNNN.json` / `round-NNNN-step-NNNN.json` / `index.steps`：落盘为 `index.json`（`schemaVersion: 3` + `results[]`）与 `results/t<TTTT>-s<SSSS>-<NN>-<tool>-<callId>.txt`；`round-NNNN.json` 仅作 **legacy 只读**兼容。下文为草案原貌。

```
<session>/tool-result-logs/
  index.json                      # rounds[] + steps[]（复用 overclock 的 steps 清单）
  round-0001.json                 # 每轮汇总（保留，兼容回退）
  round-0001-step-0003.json       # 每步一个文件（复用 stepFileName）
  results/0001-<callId>.txt       # 单条结果全文（供 read/grep 直接访问）
```

- 单条全文**落成纯文本文件**，而不是塞进 JSON：模型可直接 `read` 分页、`grep` 检索 —— 复用宿主既有语义，不需要教它新工具。
- 这与 DSH `dsh-spill-policy` 的做法一致（spill → 通知里给路径 → `read`/`grep` 取回）。
- 若采纳此结构，`read_tool_result_log` 可以**退化为索引查询**（只回答「第 N 轮第 M 步有什么」），或者**整体删除**，省一份工具定义的系统提示词。

### 3.5 明确不做的事

- **不做事后 replace**（不改写任何已发送的 `tool/result`）—— 这是本方案与 overclock/0.7.0 的分界线。
- **不改写 assistant 消息或 reasoning** —— 那是模型输出，是语义承重件；且有损处理会放大约束违反（`Governance Decay`，arXiv 2606.22528：约束违反率 0% → 压缩后 30%）。
- **不碰 `read`** —— 当步必需内容不做准入裁剪。
- **不做 LLM 摘要** —— `The Complexity Trap`（arXiv 2508.21433）实测 observation masking ≥ LLM 摘要且成本减半；`CliffCompaction`（arXiv 2609.26779）明确「从不 rephrase/rewrite」。收据 + 截断足够。

## 5. 实施路线（每步含验证点）

### 5.0 验证环境：虚拟工作区（不影响现实业务）

**为什么必须隔离（实测的现状）**：

- 真实 profile `~/.dsh/profiles/web/`：`cordis.patch.yml` 是空 `[]`（未挂插件），但 `node_modules/dsh-overclock-anchor` 是**悬空符号链接** → `/Users/mars/Workspace/github/dsh-clear-tool-results/plugins/overclock-anchor`（该目录已在 0.7.0 清理时删除）。这正是 overclock 时代的耦合方式：**symlink 直链项目目录，改代码即影响正在运行的真实环境**。
- 插件状态在 `~/.dsh/clear-tool-results.json`（当前 `{"enabled": false}`），与会话日志、spill 同处真实的 `$DSH_HOME`。

**约定**：

1. 代码改动只在项目仓库内进行（项目根 = 本仓库）。
2. 验证时**复制**（**不用 symlink**）到虚拟工作区，用独立 `DSH_HOME` 起独立实例。
3. 虚拟工作区自带独立的 `profiles/`、`sessions/`、插件状态文件 ⇒ 真实 `~/.dsh` 与正在运行的 GUI **零接触**。
4. **位置（已测定）**：`<repo>/.sandbox/` —— 放在仓库内而不是 `~/Workspace/test/`，原因是沙箱写权限只覆盖工作区，项目外每次读写都要单独授权；隔离的实质是**独立 `DSH_HOME`**，与目录位置无关。`.sandbox/` 已加入 `.gitignore`。
5. 实际布局（已建）：

```
<repo>/.sandbox/
  .dsh/                              # DSH_HOME：完全独立
    .credentials.yaml -> ~/.dsh/.credentials.yaml   # 只读共享凭据（不复制内容）
    profiles/web/                    # 复制 profile 配置 + node_modules 软链到真实（只读）
    profiles/headless/               # 一次性任务 profile（自测用）
    profiles/node_modules -> ~/.dsh/profiles/node_modules
    sessions/                        # 独立会话日志（可整体删除）
    clear-tool-results.json          # 独立插件状态
  plugin/                            # 从仓库复制的改造版插件（index.mjs / package.json / cordis.patch.yml）
  plugin-patch.yml                   # --patch overlay：只在沙箱实例挂载插件，不改真实 profile
  workspace/                         # 被测“业务项目”目录（agent 的 cwd）
```

6. 启动方式（一次性任务，跑完即退，不常驻服务）：

```sh
cd <repo>/.sandbox/workspace
DSH_HOME=<repo>/.sandbox/.dsh dsh --profile headless \
  --patch <repo>/.sandbox/plugin-patch.yml "<任务>"
```

注意：`plugin-patch.yml` 的 `name` 必须指向**文件**（`.../plugin/index.mjs`）——Cordis loader 走 ESM，目录导入会 `ERR_UNSUPPORTED_DIR_IMPORT`。
7. 复制方向固定为**仓库 → `.sandbox/plugin/`**，单向；验证产生的会话日志、落盘结果全部留在 `.sandbox/.dsh/sessions/` 内。

**第 0 步 · 复现基线与观测层（不改任何行为）**
- 从 `ed8aab1^` 恢复：`archiveStep` / `stepFileName` / `index.steps` / `readByStep` / `collectStepData` / 整轮合并；恢复 `usage.mjs` 五渠道归因（作为独立观测模块，不改清除/取回行为）。
- 验证：在测试会话里跑一轮，确认 `round-NNNN-step-MMM.json` 按步生成；`usage.json` 能报出五个渠道的比率。
- **风险**：`usage.mjs` 依赖 `session/event` 的 `step` 字段 —— 先确认当前核心仍带 `data.step`（0.6.8 的字符串编号修复即为此）。

**第 1 步 · 准入端原型（只加 `tools/post-execute`，与现有插件并存）**
- 只对 `bash` / `grep` / `glob` / `web_fetch` 生效，超阈值 → 落盘 + 收据；其余工具原样放行。
- 落盘位置先写 `$TMPDIR` 下的独立目录，避免与现有 `tool-result-logs` 混淆。
- 验证：一次真实排查会话中，`usage.json` 的 `carryText` + `carryReasoning` 比率是否下降（对照 0.7.0 的 52.6%）；取回是否走 `read`/`grep`（新增渠道计数）。

**第 2 步 · 收据四要素 + 落文件（替换 JSON 归档）**
- 单条结果写纯文本文件；`index.json` 保留 `steps[]` 做索引；收据里给绝对路径 + 取回提示。
- 验证：模型能否在**不教新工具**的前提下用 `read`/`grep` 取回（这决定 `read_tool_result_log` 能否删掉）。

**第 3 步 · 决定现有插件的去留**
- 三种可能：(a) 前置过滤上线后，事后清除直接关闭（插件退化为纯归档）；(b) 保留清除作为兜底（应对 `read` 这类不能裁剪的工具）；(c) 完全替换。
- 验证：主指标（见 §6）达标后再决定，不预判。

## 6. 成功标准（可测）

- **主指标**：未被复引的 tool result 字节数 —— 前置过滤下这部分**从未进入上下文**（对比 0.7.0：100% 先进注意力预算，事后清掉后 90.2% 再未被引用，实测 a293efee 净清除 488,821 字节 / 唯一一次取回 48,140 字节）。

| 场景 | 工具调用 | 上下文里的工具结果字节 | 净值 |
|---|---|---|---|
| **A** 问价格细节（收据预览不够用）· 插件 ON | `web_fetch` + **`read`** | 1,712（收据）+ 5,099（取回）= **6,811** | **净亏**：比基线多 1,398 B，且多一轮 |
| **B** 同一问题 · 插件 OFF（基线） | `web_fetch` | **5,413** | — |
| **C** 只问页面标题（预览够用）· 插件 ON | `web_fetch` | **1,712** | **净赚 3,701 B（−68%）**，轮次不变 |

提示词峰值：A = 10,067；B = 9,264。

**模型确实用上了预留结果**：A 里它写入参 `read <收据给出的绝对路径>` 取回全文（`read 取回 1 次，命中落盘文件`），没有重跑命令、没有要求新工具；C 里它从收据预览第一行直接拿到标题、**没有取回**。这是 0.7.0 旧机制从未达到的（旧机制 9 个真实会话只有 1 次取回）。

### 6.5.4 结论：净收益由「预览命中率」决定，不由削减字节决定

- 预览够用 → 只付收据成本，赚 ~68%；
- 预览不够用 → 收据 + 取回全文都留在上下文，**比不裁剪更差**，还要多一轮；
- 因此「按大小触发」本身不是正确的判据。当前样本命中率 1/2，不能外推。

**可选的改进方向**（未实施，待决策）：
1. **收据更小**：1,712 B 对 5,413 B 的结果占 32%，压到 ~400 B 可让亏损场景几乎消失；
2. **预览更准**：`web_fetch` 给正文段落而非含导航的原始前 32 行；
3. **按工具分设阈值**：`bash`/`grep` 的预览命中率高（尾部即成败、命中行即答案），`web_fetch` 低；
4. **引导按需取回**：收据里明确「先用 offset/limit 或 grep 取片段，不要整读」——A 里模型整读了 5,099 B。

### 6.5.5 沙箱环境（踩过的坑，供复现）

1. `plugin-patch.yml` 的 `name` 必须指向**文件**（`.../plugin/index.mjs`）——指向目录会 `ERR_UNSUPPORTED_DIR_IMPORT`。
2. 独立 `DSH_HOME` 没有凭据 → `.credentials.yaml` 软链到真实文件（不复制内容）。

## 6.6 评估：是否实现了上下文优化的目的

### 6.6.1 判据

按字节口径，单条被收据化的结果（原文 `S`）：
- 模型**不取回** → 上下文里是收据 `R` ⇒ 省 `S − R`
- 模型**取回** → 上下文里是收据 `R` + 全文 `S` ⇒ 亏 `R`，另加一轮开销 `C`

取回率 `p` 下的期望收益 `E = (1−p)·Σ(S−R) − p·n·(R+C)`，平衡取回率 `p* = Σ(S−R) / (Σ(S−R) + n(R+C))`。
实测参数：`R = 1,712` B、`C = 803` B（取自 §6.5.3 的 A/B 提示词峰值差）。

数据：全机器 78 会话、受影响工具结果（已排除 `read`/`edit`/`write`/`present`/`read_tool_result_log` 等豁免）2,296 条 / 8,356,767 B。

### 6.6.2 各阈值的平衡点（字节，正 = 省）

| 阈值 | 收据化条数 | 原文总字节 | **p\*** | p=0.3 | p=0.5 | p=0.7 | p=0.9 |
|---|---|---|---|---|---|---|---|
| 2048 | 880 | 7,292,472 | 72.3% | +3,386,178 | +1,786,356 | +186,534 | −1,413,289 |
| **4096** | **493** | **6,153,647** | **81.1%** | **+3,344,773** | **+2,034,868** | +724,963 | −584,942 |
| 8192 | 231 | 4,611,843 | 87.9% | +2,777,170 | +1,817,703 | +858,236 | −101,231 |
| 12000 | 158 | 3,902,893 | 90.1% | +2,423,467 | +1,617,514 | +811,560 | +15,607 |
| 20000 | 76 | 2,663,524 | 93.0% | +1,716,046 | +1,171,136 | +626,226 | +81,315 |
| 32768 | 46 | 1,874,853 | 93.9% | +1,222,564 | +840,206 | +457,847 | +575,489 |

**4096 的 p\* = 81.1%**——只要真实取回率低于 81% 就净赚。这比 §6.5.3 那次实测样本（5,413 B，p\*≈59%）乐观得多，因为全量数据里被收据化的结果**平均 12,482 B**，`R/S` 只有 14%。

### 6.6.3 脆弱区：刚过阈值的那一档

| 大小档 | 条数 | 平均 | p\* |
|---|---|---|---|
| 4,096–6,000 B | 143 | 5,006 B | **56.7%** |
| 6,000–8,192 B | 119 | 6,939 B | 67.5% |
| 8,192–16,384 B | 130 | 11,529 B | 79.6% |
| 16,384–32,768 B | 55 | 22,511 B | 89.2% |
| ≥32,768 B | 46 | 40,757 B | **93.9%** |

§6.5.3 踩雷的样本（5,413 B）正落在最脆弱的一档（p\* 仅 56.7%）。该档占条数 29%、字节 11.6%——**大部分字节其实很稳健**（p\* 80~94%）。

### 6.6.4 按工具（4096 阈值）

| 工具 | 收据化 | 涉及字节 |
|---|---|---|
| `run_code` | 215 / 716 | 2,296,439 |
| `web_fetch` | 92 / 107（86%） | 1,671,312 |
| `bash` | 157 / 1,294 | 1,602,617 |
| `cordis_inspect_query` | 17 / 25 | 501,757 |
| `grep` | 11 / 104 | 76,578 |

参考：全部工具结果 14,396,015 B（受影响集合占 58%，其余主要是豁免的 `read`）。

### 6.6.5 结论

**字节口径上成立，但成立与否取决于一个尚未测准的量：取回率。**

- ✅ **能达成**：取回率 ≤ 50% 时省 **2.03 MB**（占全部工具结果字节 14%）；≤ 30% 时省 3.34 MB。这部分是「一次性数据**从未进入上下文**」的削减，性质不同于旧机制（先进上下文、后清除）。
- ✅ **大结果稳健**：≥8,192 B 各档 p\* 都有 80~94%，即使模型几乎总要取回也仍然赚。
- ⚠️ **临界区脆弱**：4,096–6,000 B 档 p\* 仅 56.7%，等于赌博。
- ⚠️ **取回率未知**：只有 3 次端到端会话（2 次触发、1 次取回 = 50%），置信度极低。**这是唯一的决定性变量，必须采数据。**
- ⚠️ **只覆盖工具结果**：`read` 等豁免工具、reasoning、assistant 输出、系统提示都未触及。用户最初的问题（模型把结果转述进推理，0.7.0 实测 52.6% 记忆代偿）在新机制下**不是消失，而是转换成取回成本**——结果从未进入上下文，模型自然无法转述，但要靠取回补齐。
- ⚠️ 本评估是**模型推算**，不是实测；`R`/`C` 各来自单次会话。假设「取回 = 读回全文」——若模型改用 `offset/limit`/`grep` 只读片段，`p*` 会更高；若多次分页取回，则更低。

### 6.6.6 建议

1. **先采数据再定阈值**：把取回率做成可观测量（收据已带路径，可在 `read`/`grep` 入参里识别是否命中 `tool-result-logs/results/`）。跑一段时间后用真实 `p` 重算上表。
2. **削脆弱区**：对 4,096–8,192 B 档提高预览质量或直接放行（该档只占字节 11.6%，放行损失有限）。
3. **降收据成本**：`R` 从 1,712 B 压到 ~400 B，可让 p\* 全线上升（`R` 同时出现在分子扣减与分母）。
4. **不追 `read`**：`read` 是豁免里最大的字节来源，但它正是「当步必需」，动它会把 p 推高到危险区。

## 7. 风险与已知缺陷

1. **当步必需全文**：`bash` 输出被截成尾部 + 收据后，若关键信息在中段，模型要多花一轮取回 —— 对「每步都必须看全文」的会话是纯损失。缓解：按工具细分（`read` 不动）、保尾、收据带行数与形状。
2. **收据的「头部」未必含关键信息**：`grep` 的关键命中可能在尾部。缓解：保留命中计数 + 每条命中行首，而不是简单 head。
3. **三条缝未收敛**：现有 `ARCHIVE_MAX_BYTES=49000` / spill `maxInlineBytes=50000` / `RENDER_BUDGET_BYTES=48000` 互不对齐，造成 `(49000, 50000]` 永久取不回、`(48000, 49000]` 归档但默认跳过。新方案应**统一到一个阈值**并让落盘上限 ≥ 准入阈值。**（已作废 · 2026-09-28：0.8.0 删除 `ARCHIVE_MAX_BYTES`，归档改为插件自写文件，两条缝不复存在。）**
4. **失败结果不能裁剪**（`isError`）—— 报错内容是排障必需，且属于「治理约束」，丢弃会推高违反率。
5. **样本问题**：0.7.0 的 52.6% 是 ≤49000 字节范围、5~173 条的观测；是否适用于全部工具未知。
